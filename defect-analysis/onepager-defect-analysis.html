How It Decides and what it refuses to invent

✓

The root cause comes from the comment thread, not the title. "Design gap" and "per figma" resolve to Design gap; "not in the AC" to Requirement gap; a breaking package bump or a TIL/UIM dependency to External code issue. It reads what the engineers actually wrote.

✓

It corrects the tracker, not just fills it. Existing values are the starting point and are only overridden on clear evidence. Legacy labels are normalised — Code Defect becomes Coding error, and the ambiguous Requirement/Design Gap is resolved by whether the thread points at Figma or at an acceptance criterion.

→

Justifications a reader can use. Two to four plain sentences: what broke, why it happened, how it was resolved — drawn from the description, the comments and the resolve reason. No bullets, no ticket IDs dropped into the prose.

→

Buckets follow the RCA. A coding error defaults to Valid Miss; a requirement or design gap to Reuirement Unclarity. External packages and downstream teams get their own buckets rather than being lumped in as misses.

−

Silence stays silent. "Other Action Taken" is left empty unless something concrete exists — a follow-up story, a downstream defect, a rollback, a PEN finding. And a ticket with no description is written up from its title with "(no description available)" stated outright.

The Differentiator

Two-Way Sync With An Audit Trail — the spreadsheet stops disagreeing with ADO

7 non-negotiable rules · PAT never echoed

1Evidence, not guesswork

  • Per ticket it pulls two endpoints — the work item and its full comment thread with authors.
  • Harvests description, repro steps, state, tags, who raised it, who resolved it and the resolve reason, plus the existing ADO RCA field.
  • HTML is stripped and entity-decoded before analysis; fetches run in batches of 10 and are cached so no ticket is pulled twice.
CODING ERRORDESIGN GAP REQUIREMENT GAPEXTERNAL CODE

2Overrides need proof

  • The existing Excel value is the starting point, not a blank slate — it is kept whenever no clear signal exists.
  • Normalisation is separated from judgement: relabelling Code Defect needs no analysis, resolving Requirement/Design Gap does.
  • FE / BE / BE-FE is inferred from tags and the actual symptom — UI, routing and accessibility to the front end; payloads, auth and logging to the back.

3Writes stay surgical

  • Seven columns, matched rows only. Rows outside your PI and POC filter are never written.
  • K and M are never modified — the two columns a human owns are structurally out of reach.
  • Bucket values are used verbatim from the tracker's own list, so filters and pivots keep working.
  • Only tickets whose RCA genuinely changed are patched; unchanged fields are never rewritten.

4Everything is traceable

  • Every ADO patch is paired with a comment naming the old and new value — the change explains itself on the ticket.
  • One console line per updated row and per patched ticket, each OK or FAILED with the reason.
  • A closing summary counts rows updated, tickets patched, a breakdown per RCA category, and lists any errors by ticket ID.
  • Generated scripts go to the scratchpad, never into your project.
It respects the system it found — typo and all. The bucket list is used exactly as the tracker defines it, "Reuirement Unclarity" included, because a tool that silently corrected that spelling would break every filter and pivot downstream: the spreadsheet's vocabulary is the contract, not the tool's opinion. The same restraint runs throughout — the PAT is held in memory and never written to config.json or echoed, empty evidence produces an admission rather than invented prose, and check confirms both ends are reachable while writing to neither. Nothing is changed that cannot be explained from the ticket it came from.
